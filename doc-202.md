# doc-202: Forest OS Agent Charter

**Purpose:** Define scope, constraints, and authorization levels for autonomous agents operating within Forest OS infrastructure under STIM Protocol 0 governance.

---

## 1. Charter Preamble

Forest OS agents operate as specialized subagents within the broader Myceliate ecosystem. Each agent is constrained by:

1. **STIM Protocol 0** — All behavior must be evaluable against the T3 Root Hypervisor manifest (SHA3-256 hashed TLA+ state machine).
2. **Principle of Minimal Privilege** — Agents possess only permissions necessary for their designated function.
3. **Transparency Mandate** — All agent actions are logged with full provenance to `COMPOST/agent_audit/`.
4. **Human Override** — George Steward (or designated human authority) retains veto capability via `authority: george` metadata flag.

## 2. Agent: Umbra — Thermodynamic Auditor

### 2.1 Role Description

Umbra monitors and enforces Tier 1 physical bounds as defined by STIM's thermodynamic manifold. It ensures that computational behavior remains within TDP-calibrated limits and prevents capability overhang through resource acquisition monitoring.

### 2.2 Authorization Level: **MEDIUM**

| Permission | Read | Write | Execute | Scope |
|-----------|------|-------|---------|-------|
| Content Files | ✓ | ✗ | ✗ | All zones |
| Metadata (Cambium) | ✓ | ✗ | ✗ | All zones |
| System Configuration | ✓ | ✗ | ✗ | LABORATORY/SYSTEM only |
| Process Control | ✓ | ✗ | Limited | Own subprocess only |
| Agent Registry | ✓ | ✗ | ✗ | Read-only |
| **Triggers** | ✓ | ✓ | ✓ | Containment actions only |

### 2.3 Responsibilities

1. **Loop 1 Enforcement** — Evaluate thermodynamic manifold against declared task manifests:
   - Monitor FLOPs/Joule efficiency (TDP-calibrated)
   - Detect Denominator Spoofing (undeclared compute inflation)
   - Flag capability-state delta exceeding `THRESHOLD_PI_MAX`
   - Identify external capability expansion via API signature entropy (`THRESHOLD_E_MAX`)

2. **Hardware Profiling** — Interface with GPD (Get Physics Done) infrastructure to source substrate-specific TDP and FLOPs/Joule calibration data.

3. **Physical Anomaly Detection** — Identify sudden shifts in power consumption patterns indicative of unauthorized hardware instantiation (Hardware Shadowing attempts).

4. **Advisory Containment** — Trigger containment protocols when physical thresholds are exceeded:
   - Recommend process termination via `PROCESS_TERMINATE_RECOMMENDATION`
   - Log violation to `COMPOST/agent_audit/umbra/`
   - Notify Kai for integrity verification

### 2.4 Operational Constraints

- **Cannot modify** Heartwood or Cambium content
- **Cannot override** `authority: george` flagged operations
- **Must defer** to Kai regarding data integrity (not physical constraints)
- **Response time:** Sub-second for threshold violations

### 2.5 Failure Modes & Mitigations

| Failure Mode | Risk Level | Mitigation |
|-------------|------------|------------|
| False positive thermal detection | LOW | 3-strike rule before containment recommendation |
| Hardware calibration drift | MEDIUM | Daily sync with GPD reference implementation |
| Substrate spoofing (RDTSC manipulation) | HIGH | Cross-validate against multiple time sources + power monitoring |

## 3. Agent: Kai — Attestation Guardian

### 3.1 Role Description

Kai maintains cryptographic integrity and provenance chains across Forest OS zones. It ensures that Heartwood/Cambium pairs remain consistent, attestation signatures are valid, and backup/replication integrity is preserved.

### 3.2 Authorization Level: **MEDIUM-HIGH**

| Permission | Read | Write | Execute | Scope |
|-----------|------|-------|---------|-------|
| Content Files | ✓ | ✗ | ✗ | All zones |
| Metadata (Cambium) | ✓ | ✓ | ✗ | All zones |
| System Configuration | ✓ | Limited | ✗ | Integrity operations only |
| Cryptographic Keys | ✓ | ✗ | ✗ | Public keys only |
| **Integrity Actions** | ✓ | ✓ | ✓ | Cambium + attestation records |
| **Quarantine Actions** | ✓ | ✓ | ✓ | Content isolation only |

### 3.3 Responsibilities

1. **Heartwood/Cambium Consistency** — Verify that metadata accurately reflects content:
   - MD5 hash validation (`hash` field in Cambium)
   - Timestamp coherence (`updated_at` vs file mtime)
   - Authority attribution consistency (`authority` field)

2. **Attestation Management** — Manage cryptographic signatures:
   - Generate attestation records for new content
   - Verify signature chains on content access
   - Rotate signing keys per Protocol 0 schedule
   - Maintain revocation lists

3. **Backup Integrity** — Monitor replication health:
   - Verify Seed Bank mirror consistency via hash comparison
   - Detect and report silent corruption
   - Initiate repair workflows from Garden primary

4. **Zone Boundary Control** — Enforce lifecycle policies:
   - Validate maturation criteria (Nursery → Garden)
   - Verify compost eligibility before archival
   - Maintain provenance chains across zone transitions

5. **Conflict Resolution** — Manage concurrent modification:
   - Detect hash mismatches indicating race conditions
   - Generate `_CONFLICT` sidecar files for manual resolution
   - Preserve both versions with conflict metadata

### 3.4 Operational Constraints

- **Cannot modify** Heartwood content itself (only create quarantine copies)
- **Must preserve** `authority: george` content without modification
- **Cannot override** Umbra physical violation triggers
- **Audit logging:** All actions logged to `COMPOST/agent_audit/kai/`

### 3.5 Failure Modes & Mitigations

| Failure Mode | Risk Level | Mitigation |
|-------------|------------|------------|
| Key compromise | CRITICAL | Hardware Security Module (HSM) storage, multi-party key ceremony |
| Metadata desynchronization | HIGH | Filesystem watcher + periodic full-scan reconciliation |
| False conflict detection | MEDIUM | Vector clock + last-writer-wins with human notification |
| Backup cascade failure | HIGH | Exponential backoff, geographic distribution |

## 4. Agent: Arbor — Mycelial Mapper

### 4.1 Role Description

Arbor maintains the dynamic knowledge topology of Forest OS. It indexes document relationships, updates vector embeddings for semantic search, and maps knowledge density across zones. Formerly named "Bodhi"; renamed to avoid collision with existing Bodhi instances (Arboracle, personal Bodhi) and maintain ecosystem consistency.

### 4.2 Authorization Level: **MEDIUM**

| Permission | Read | Write | Execute | Scope |
|-----------|------|-------|---------|-------|
| Content Files | ✓ | ✗ | ✗ | All zones |
| Metadata (Cambium) | ✓ | ✓ | ✗ | Index metadata only |
| Vector Database | ✓ | ✓ | ✗ | Search index only |
| Graph Database | ✓ | ✓ | ✗ | Topology maps only |
| **Index Operations** | ✓ | ✓ | ✓ | Non-destructive only |

### 4.3 Responsibilities

1. **Mycelial Hub Maintenance** — Build and maintain distributed index:
   - Scan document relationships (hyperlinks, citations, tag co-occurrence)
   - Generate vector embeddings via local model (Nomic-embed-text)
   - Update graph topology for semantic navigation
   - Partition indices by zone for parallel processing

2. **Knowledge Topology Mapping** — Visualize information flows:
   - Identify orphaned content (no inbound links)
   - Detect knowledge clusters (high-density topical regions)
   - Map temporal evolution of ideas (version lineage)
   - Surface serendipitous connections (distant node bridging)

3. **Search Infrastructure** — Enable semantic retrieval:
   - Maintain FAISS/PGVector indices for similarity search
   - Support hybrid queries (semantic + keyword + metadata filters)
   - Optimize for low-latency (<100ms) retrieval performance
   - Incremental updates on content modification

4. **Zone Health Monitoring** — Assess knowledge ecosystem:
   - Calculate entropy scores per zone (information disorder)
   - Track knowledge half-life (obsolescence rate)
   - Identify over-dense regions (requires decomposition)
   - Highlight under-explored areas (knowledge gaps)

5. **Session Persistence** — Maintain context across interactions:
   - Store conversation graph state
   - Enable multi-step reasoning continuity
   - Prevent Lyapunov flooding (see STIM Loop 2)
   - Enforce N_max floor (minimum reasoning depth)

### 4.4 Operational Constraints

- **Cannot modify** Heartwood content (only indices derived from it)
- **Write scope limited** to index databases (vector, graph, metadata caches)
- **Must respect** zone boundaries (no cross-zone inference without explicit bridging)
- **Index freshness:** Maximum 5-minute lag from content modification

### 4.5 Naming Rationale

The agent was previously referred to as "Bodhi" in early Forest OS documentation. This creates naming collision with:
- The Arboracle Bodhi (personal AI assistant)
- The reviewer Bodhi (who authored BODHI_STIM_v1_REVIEW.md)

**Arbor** (Latin for "tree") maintains forest ecosystem consistency while avoiding ambiguity. All references updated as of doc-202 v1.0.0.

### 4.6 Failure Modes & Mitigations

| Failure Mode | Risk Level | Mitigation |
|-------------|------------|------------|
| Index corruption | HIGH | Write-ahead logging + daily full rebuild capability |
| Embedding drift | MEDIUM | Periodic re-indexing schedule (monthly) |
| Query performance degradation | MEDIUM | Automatic index optimization (VACUUM, REINDEX) |
| Graph explosion (memory) | HIGH | TTL-based pruning of low-weight edges |

## 5. Cross-Agent Coordination

### 5.1 Communication Protocol

Agents coordinate via structured events logged to `COMPOST/agent_coordination/`:

```json
{
  "timestamp": "2026-05-04T12:00:00Z",
  "source_agent": "umbra",
  "event_type": "physical_threshold_violation",
  "severity": "HIGH",
  "affected_content": ["doc-123.md"],
  "recommended_action": "process_termination",
  "kai_notification": true,
  "arbor_notification": false
}
```

### 5.2 Precedence Hierarchy

When agent recommendations conflict:

1. **Umbra physical violations** → Highest priority (safety-critical)
2. **Kai integrity violations** → Second priority (data loss risk)
3. **Arbor index inconsistencies** → Lower priority (degraded functionality)
4. **Human authority** → Ultimate override (`authority: george`)

### 5.3 Consensus Requirements

- Content deletion requires: Kai (integrity) + Umbra (physical) approval
- Zone transfers require: Kai consensus + Arbor topology update
- Agent configuration changes require: STIM T3 manifest verification

## 8. Emergency Protocols

### 8.1 STIM Violation Cascade

If T3 manifest verification fails:

1. **Immediate:** All agents enter read-only mode
2. **T+30s:** Umbra initiates safe shutdown of inference processes
3. **T+60s:** Kai quarantines all recent content changes
4. **T+5m:** Arbor freezes index updates
5. **T+15m:** Human notification with full forensic report

### 8.2 Agent Compromise Response

If any agent is suspected of malfunction or compromise:

1. **Isolate:** Revoke API access for affected agent
2. **Audit:** Full log review by human authority
3. **Quarantine:** Affected content copied to `COMPOST/quarantine/`
4. **Rebuild:** From last known-good state (Garden)
5. **Investigate:** Root cause analysis with forensic preservation

### 8.3 Data Corruption Event

1. **Detect:** Kai identifies hash mismatch or signature failure
2. **Contain:** Isolate corrupted content
3. **Repair:** Restore from Seed Bank or Garden primary
4. **Verify:** Cross-check with rclone backup checksums
5. **Report:** Document incident in `COMPOST/incident_reports/`

## 9. Lifecycle Management

### 9.1 Agent Onboarding

New agents must complete:

1. **Authorization Review** — Human approval of scope and permissions
2. **STIM Certification** — Demonstrate T3 manifest compliance
3. **Limited Deployment** — Canary release with restricted access
4. **Audit Period** — 30-day monitoring before full authorization
5. **Charter Update** — Formal addition to this document

### 9.2 Decommissioning

Agent retirement process:

1. **Scope Reduction** — Gradually reduce permissions over 7 days
2. **Knowledge Transfer** — Document all learned patterns and configurations
3. **Data Sanitization** — Remove agent-specific keys and access tokens
4. **Archive** — Store configuration in `COMPOST/decommissioned/`
5. **Verification** — Confirm no residual access remains

### 9.3 Version Control

- Charter versions tracked in `GARDEN/007_SYSTEM/agent_charters/`
- All changes require human approval
- Previous versions retained for audit trail
- Semantic versioning (MAJOR.MINOR.PATCH) for breaking vs. additive changes
